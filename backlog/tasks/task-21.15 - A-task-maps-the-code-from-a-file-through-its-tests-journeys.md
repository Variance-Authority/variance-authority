## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
An agent in a file (the payment controller) with a task in words (how payment is used in checkout) gets a codemap built from test journeys: every test that entered the file, across all declared suites; the tests the task keeps; their journeys with suite-wide structure removed; and the spine those kept tests share, drawn as where the flow starts, what it passes through, and where it goes, each place named by the tests that lead there. The task is the filter; nothing else decides which tests are kept. Journeys are read from the prepared recording; nothing runs at question time. Target is what Windsurf codemaps promised: a task-specific map of the code, here built from what ran rather than from text.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 From a file and a task, the answer lists how many tests entered the file, how many the task kept, and names the kept ones
- [ ] #2 Regions most of the whole suite enters are counted as structure and not drawn; the denominator is stated
- [ ] #3 The spine (regions most kept tests enter and the suite does not) is drawn first, in the order the journeys pass through it, with branches beyond it named by the tests that take them
- [ ] #4 Every place in the map is a file and declaration with the tests that reached it; nothing in it comes from reading source text or running a test
- [ ] #5 The owner judges one map on this repository and one on a corpus repository as useful before the answer ships

Masks replace callers (scratchpad masks.mjs). A journey is the set of blocks one test ran. Sort by size, cluster identical masks, match each mask against A and B. The smallest mask that holds both is the connection. The near-miss cluster is the journeys that reached one end and share at least half of a journey that reached both. A fork is a block inside a function most of both groups ran, scored by how well it separates the groups. What differs outside the forks is downstream of them. Runs in 0.15 s per pair.

At file grain the same hubs split into 159-333 paths, so the projection must be the function (and the functions of its forks), never the file or the whole journey.
- The majority path is passage, usually the entry block or an early return: styleFunctionSx :101 with no sx, getThemeProps :43. This is the over-testing reading at that function.
- The minority paths carry meaning, and their test names state the path. styleFunctionSx: 'using sx color as a function should not crash'. getThemeProps: 'respect custom default props', 'ownerState is used in styleOverrides'.
- Meaning is not size and not solitary-versus-social. The meaningful tests are social component tests (median 62-139 functions), and the passage tests are no bigger (median 91, smallest 11). Size picks the story within a path cluster, never across clusters.
- The codemap should collapse the majority path into one row ('N pass through, :line returns') and expand each minority path with its smallest test.
