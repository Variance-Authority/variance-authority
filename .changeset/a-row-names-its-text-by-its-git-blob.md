A coverage record names the text each module row was cut from by the name git gives it, in a new `modules.blob` section of record format 12: the landing reads it from the commit for a file the working tree agrees with and from `git hash-object` for a changed one, so a file git cleans on the way in (`core.autocrlf`, a filter) is named as the source index names it. Format 11 records still open, with no text named. `variance coverage` compares that name with the one the source index gives the file now, hashing no text, and reads two texts only to diff them where their names differ. Outside CI `variance coverage` and `variance review` bring the source index up to the checkout before they read it, saying nothing unless that fails, and every other reader takes the index as it stands; when it fails, the index is read as it stands, one line names the failure, and every region run counts as not known with that failure as the reason, while the rest of the answer, the source section and `--from` among it, stands. `variance review` then says, with that failure, that which text the record ran over is not known, and reads its rows as the cases that stood on the changed lines. A file the source index would read and does not hold, which git does not ignore and the disk does not hold, is gone, so every region run in it counts over an older text; one the index does not read, one git ignores, and one still on disk count as not known, each with that reason. A file whose rows name no text — a record made before format 12, a JVM record, a file edited again before its run landed — counts its regions run as not known, with that reason. In CI it takes the source index as the pipeline published it and builds none; with no index to have, it reads no text, and every region run counts as not known because no source index names the checkout's texts.
