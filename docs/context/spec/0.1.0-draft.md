# Variance Authority — Development Specification

**Version:** 0.1.0-draft
**Status:** Kickoff
**Domain:** variance-authority.dev

The source specification as received at kickoff, recorded verbatim. Amendments
live in ADRs, which reference the section they amend. This file is not edited.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted
as described in RFC 2119.

---

## 1. Thesis

Existing visual regression tools answer *"did pixels change?"* and bill by the
screenshot. Variance Authority answers *"what changed, why, where, and should
anyone care?"* — and answers it at the cheapest representation capable of
deciding, in the user's own infrastructure.

The atomic unit of output is not an image diff. It is an attributed sentence:

> **`Button` (variant prop change) → propagated to `NewHero` → visible in right
> panel — band: token, verdict: authorized.**

Pixels are not the workload; pixels are the alarm. A pixel-level change that
cannot be explained semantically is the *highest*-severity signal in the system,
not the routine one.

### 1.1 Positioning

- **Category:** deterministic verification layer for frontend surfaces,
  purpose-built for the agent-driven development era.
- **Primary consumers:** AI coding agents (via skill + MCP/CLI) and CI pipelines
  (via GitHub Action). Humans consume summaries, not screenshot galleries.
- **Anti-positioning:** not a hosted screenshot store, not per-screenshot
  pricing, not an AI/ML perceptual differ. All diffing is deterministic.

### 1.2 One-line pitch

*Percy shows you pixels. Variance Authority tells you Button broke the hero.*

## 2. Glossary

| Term | Definition |
|---|---|
| **Subject** | A renderable unit under observation: a story, a page route, or a component fixture. |
| **Surface** | The full set of promises a package or app exposes: semantic render, API surface, tokens, and (optionally) raster. |
| **Semantic snapshot** | Normalized serialization of a subject's rendered state: ARIA tree + normalized computed styles + layout rects, annotated with provenance. |
| **Render hash** | Content hash of a semantic snapshot combined with the environment key. |
| **Environment key** | Hash of all non-code render inputs: browser engine + version, font set, viewport, media/feature flags, external asset hashes. |
| **Baseline** | An *approved* render hash (plus its snapshot) recorded in the manifest. Content-addressed, not branch-addressed. |
| **Band (frequency)** | Severity/kind classification of a change: `geometry`, `token`, `texture` (see §5). |
| **Provenance chain** | Owner path from a DOM node to its React component chain with props at each boundary, derived from the fiber tree. |
| **Root / collateral** | A change whose explanation originates in a subject's own inputs (root) vs. a change fully explained by an upstream root (collateral). |
| **Explanation set** | The minimal set of upstream deltas that account for a subject's semantic diff. |
| **Verdict** | Machine-readable adjudication for a change set: `unchanged` \| `inherited` \| `authorized` \| `needs-review` \| `violation` \| `unexplained`. |
| **Docket** | The grouped, per-root-cause presentation of all variance in a change set. |
| **Manifest** (`variance.lock`) | Git-committed record of approved baselines, policies, and surface declarations. |

## 3. Core Principles (normative)

1. **Cheapest-representation-first.** The system MUST decide each subject's
   verdict at the cheapest stage capable of deciding it, and MUST NOT compute
   more expensive representations for subjects already decided.
2. **Determinism.** All collectors and differs MUST be deterministic: same inputs
   ⇒ byte-identical outputs. No ML/perceptual components in the verdict path.
3. **BYO everything.** The system MUST NOT require vendor-hosted storage or
   compute. Artifacts live in the user's CI artifacts / object store; baselines
   and manifests live in git. There is no per-asset billing surface by design.
4. **Content addressing.** Baselines MUST be addressed by content (render hash),
   never by branch or commit topology. An approved hash is approved everywhere;
   rebases and merges MUST NOT invalidate baselines.
5. **Attribution by construction.** Causality flows forward through the pipeline
   (code → semantic → raster). The system MUST never infer cause from pixels; it
   carries provenance so that every change already has a name when it reaches
   raster.
6. **Adjudicate once.** A change adjudicated at the layer that owns it
   (component, package, design system) MUST resolve as `inherited` at all
   consuming layers.
7. **Policy over judgment.** Which changes matter, where, and at what band is
   declared in advance as project policy — the tool enforces; it does not opine.
8. **Independent adoptability.** Each dimension (semantic render, API surface,
   tokens, raster) MUST work standalone. The unified verdict is opt-in
   composition, not a monolith.

## 4. System Architecture

### 4.1 Pipeline stages

```
             ┌────────────────────────────────────────────────────┐
  changed    │ Stage 0: REACHABILITY                (module graph)│
  files ───▶ │ unaffected subjects → verdict: unchanged (inherit) │
             └───────────────┬────────────────────────────────────┘
                             │ reachable subjects
             ┌───────────────▼────────────────────────────────────┐
             │ Stage 1: SEMANTIC RENDER          (headless render)│
             │ serialize → normalize → hash → compare to manifest │
             │ hash match → verdict: unchanged (cache hit)        │
             │ hash miss  → semantic diff + banding + attribution │
             └───────────────┬────────────────────────────────────┘
                             │ semantically-unexplained residue only
             ┌───────────────▼────────────────────────────────────┐
             │ Stage 2: RASTER                      (screenshots) │
             │ pixel diff → region→owner projection → attribution │
             │ still unexplained → verdict: unexplained (alarm)   │
             └────────────────────────────────────────────────────┘
```

**Stage 0 — Reachability.** Input: git diff + module dependency graph. Subjects
not reachable from changed files inherit their prior verdict with zero work.
Granularity: file-level at minimum; export-level reachability MAY refine it
later. Lockfile/config changes conservatively mark all subjects reachable (a
known TurboSnap weakness the semantic stage then absorbs cheaply).

**Stage 1 — Semantic render.** For each reachable subject, render headless and
serialize the semantic snapshot (§4.2). Hash with the environment key. Manifest
hit ⇒ `unchanged`; **no screenshot is ever taken for a hash hit.** On miss,
compute the structural diff against the baseline snapshot, classify each delta
into a band (§5), and run attribution (§6). Most misses terminate here: the
semantic diff *is* the report ("padding 8→12 on `Card`, source: `tokens.css:41`").

**Stage 2 — Raster.** Only subjects with semantically-unexplainable deltas — or
regions declared raster-mandatory by policy (canvas, WebGL, images, filters) —
are screenshotted. Pixel diff regions are projected through the layout map back
to owner chains (§6.3). Residue with no owner-attributable semantic cause yields
`unexplained`, the highest-severity verdict.

### 4.2 Semantic snapshot format

The snapshot is a normalized tree. Per node:

- **role/name/state** from the accessibility tree (Playwright `ariaSnapshot` as
  the base primitive);
- **normalized computed styles**: a curated, versioned property allowlist
  (layout, box, color, typography, visibility), with values canonicalized
  (colors to a single space, lengths resolved to px, custom-property
  *resolutions* recorded alongside the custom-property *names* that produced
  them);
- **layout rect** (x, y, w, h) per viewport;
- **provenance**: owner component chain + props-at-boundary digest (§6.1);
- **content digest** for text nodes.

**Normalization rules (the moat — MUST be public, versioned, and test-covered):**

- generated class names, style-hash attributes, and framework-internal
  attributes are stripped;
- non-semantic wrappers (no role, no visual effect on the box tree) are
  collapsed;
- unordered attribute/property maps are serialized in canonical order;
- animation/transition state is captured at a declared settle point (animations
  disabled or forced to end state);
- timestamps, random ids, and declared-volatile regions are masked per policy.

The normalization ruleset version is part of the environment key: changing the
rules is itself a mass-invalidation event and MUST be treated as such (§9).

### 4.3 Storage model

- **Manifest (`variance.lock`)** in git: approved render hashes per subject ×
  environment key, policy references, surface declarations. Small, text,
  mergeable; merge conflicts resolve at subject granularity.
- **Snapshot store** (user's CI artifacts / S3 / R2, content-addressed by hash):
  full semantic snapshots for diffing and review. Prunable; the manifest alone
  suffices for pass/fail.
- **Raster store** (user's bucket): transient screenshots for the review surface
  only. Retention is user policy; approved states are *never* stored as images,
  only as hashes + snapshots.

### 4.4 Dimensions beyond render

Each is a standalone collector emitting a diffable text report into the same
verdict model:

- **API surface:** TypeScript API report (api-extractor-class extraction),
  `exports` map, publint/attw-class packaging checks. Deltas banded as
  `breaking` / `additive` / `internal` and mapped to required semver.
- **Design tokens:** resolved token table (name → value per theme). Token deltas
  are first-class roots for attribution in Stage 1.
- **Bundle/module graph:** size, new transitive deps, duplication. (Post-v1.)
- **Docs drift:** declared API vs. actual API. (Post-v1.)

## 5. Frequency Bands

Every semantic delta is classified into exactly one band. Bands drive default
severity and review policy.

| Band | What changed | Detection representation | Default policy |
|---|---|---|---|
| **geometry** (low freq) | boxes appear/disappear/move/resize; ARIA structure; content reflow; role/name/state changes | layout rects + ARIA tree | always surfaces; blocking unless declared in intent |
| **token** (mid freq) | style *values* changed, structure held: color, spacing, typography, radius, shadow values | computed-style diff, keyed to token names where resolvable | surfaces **once per root**; collateral folded under it |
| **texture** (high freq) | sub-semantic rendering variance: anti-aliasing, sub-pixel shifts, compression artifacts | raster residue after semantic explanation | auto-pass; counted for frequency stats; never reviewed |

**Band thresholds are policy, not constants.** Policy MAY promote or demote bands
per project, per subject, per region, per component (e.g., design-system repo:
`token` is blocking; marketing hero: `geometry` demoted to advisory).

**Frequency statistics.** Per-node and per-component change frequency across
builds is accumulated (hash-level, no images opened). Chronically unstable
regions are reported for demotion/masking; a region that changes in most builds
is noise by definition and the tool SHOULD say so.

## 6. Attribution and Provenance (React-first)

### 6.1 Fiber instrumentation

At snapshot time, the renderer harness walks the React fiber tree (DevTools
global hook / bippy-style traversal) and annotates every serialized DOM node
with:

- owner component chain (`Button ← Header ← CheckoutPage`), using displayName;
- props digest at each component boundary (stable hash of serializable props);
- optional source location via a babel/swc plugin (click-to-component-style),
  enabled per project.

Instrumentation runs only in the snapshot environment; production builds are
untouched.

### 6.2 Explanation sets and root/collateral

For every changed subject, the attributor computes the minimal explanation set:
which upstream deltas (a token value, a component's internal subtree, a prop
change at a boundary) account for the semantic diff.

- Diff originates **inside** a component's subtree with unchanged incoming props
  ⇒ internal change; that component is the **root**.
- Diff explained entirely by **changed props at a boundary** ⇒ composition
  change; root is the prop provider.
- Diff explained by a **token/style source delta** ⇒ the token is the root; all
  affected subjects are collateral.
- A subject MAY carry both an inherited collateral delta and its own root delta;
  the docket lists them separately.

The docket presents one entry per root: *root cause, band, count of collateral,
sample subjects, owner chain.* "1 token change, 300 collateral, structure intact"
is one review item, and its approval flow MUST be one action.

### 6.3 Pixel → component projection

component → DOM (fiber) → rect (layout) → screen region composes into an
invertible-in-practice map from pixel coordinates to owner chains. Stage-2
pixel-diff regions are intersected with the layout map; clustering is by
**component identity**, not visual fingerprint similarity. Spatial location is
expressed via ARIA landmarks ("right panel", "navigation", "dialog"), not
coordinates.

Where regions overlap ambiguously (transforms, portals, filters, stacked
layers), the projection MUST report the candidate owner set with an ambiguity
flag rather than guessing. Pixel-fingerprint clustering (Argos-style) is the
declared **fallback** for the ambiguous/unattributable residue only.

### 6.4 Hierarchy: adjudicate once

- **Component vs. page:** a page's diff fully explained by an already-adjudicated
  component change ⇒ page verdict `inherited`. A page owns only its composition
  variance (arrangement, presence, inter-component layout interaction).
- **Design system vs. product:** a product repo consumes the DS's published
  manifest as trusted upstream. DS-attributed deltas in product subjects resolve
  as `inherited` referencing the DS adjudication. Policies are per-repo: DS
  strict, product loose.
- Cross-repo trust is expressed by pinning the upstream package version + its
  manifest digest.

## 7. Verdict Model and Policy

### 7.1 Verdicts

| Verdict | Meaning | Typical consumer action |
|---|---|---|
| `unchanged` | hash hit or unreachable | none |
| `inherited` | fully explained by an upstream adjudication | none |
| `authorized` | change matches declared intent / policy auto-approves band | proceed; baseline updated on merge |
| `needs-review` | band+policy requires sign-off | human approves root (one action per root) |
| `violation` | policy forbids (e.g., breaking API without major bump; geometry change in protected region) | agent MUST fix before PR / CI blocks |
| `unexplained` | raster residue with no semantic cause | highest severity; investigate |

### 7.2 Policy file (`variance.config`)

Declares, per project and overridable per subject/region/component:

- band severity mapping (which bands block, advise, or auto-pass);
- protected regions/components (promote), volatile regions (mask/demote);
- dimension enablement (semantic, API, tokens, raster) and raster-mandatory
  regions;
- required approvers per band (post-v1, hosted tier);
- intent contract: how a PR/agent declares intended change classes, enabling
  `authorized` verdicts (e.g., changeset-style intent file: "this PR changes
  token `--color-primary`").

The policy file is the product's expression of "authority": not judging every
change, but declaring in advance which ones deserve judgment.

### 7.3 Mass invalidation

Engine bumps, font-set changes, normalization-ruleset upgrades, and global token
changes invalidate at environment-key or root scale. Required UX from day one:
the docket MUST collapse such events to a single root ("chromium 126→127",
"ruleset v3") with **one-action re-baselining** of all collateral, plus a sampled
spot-check list (policy-configurable sample size) so approval is informed, not
blind.

## 8. Delivery Surfaces

1. **CLI (`va`)** — the core. `va collect`, `va diff`, `va verdict`,
   `va approve <root>`, `va baseline`. All output dual-format: human summary +
   JSON. Runs anywhere Playwright runs.
2. **GitHub Action** — wraps the CLI; posts the docket as a PR comment + status
   check per policy. Artifacts to the user's storage; nothing leaves their infra.
3. **MCP server** — exposes the deterministic tools (`collect_semantic`,
   `diff_surface`, `get_verdict`, `explain_change`, `approve_root`) for agent
   orchestration. Tools measure; they never opine.
4. **Agent skill** — the adjudication guidance layer: how an agent should
   interpret verdicts against its stated intent, when to self-correct before
   opening a PR, how to declare intent for `authorized` outcomes. The skill is
   guidance; the verdicts are guardrails.
5. **Review surface (post-v1, first paid tier)** — hosted UI over user-stored
   artifacts: docket review, org policy, audit trail, approvals. Monetization is
   the collaboration/governance surface (oasdiff/Codecov model), never per-asset.

## 9. Non-Goals and Explicit Exclusions

- **No hosted image storage. No per-screenshot billing.** Structural, not just
  initial.
- **No ML/perceptual diffing** in the verdict path, ever. Determinism is the
  brand.
- **No framework-agnostic launch.** React-first; fiber provenance is the moat.
  Other frameworks later as provenance-provider adapters behind the same
  interface.
- **No monolithic "adjudicate everything" v1.** Dimensions ship independently
  adoptable; the unified verdict is opt-in.
- **No cross-browser matrix at launch.** One pinned engine (Chromium) per
  environment key; additional engines are additional environment keys later.
- **No reinvention of collectors** where excellent narrow tools exist
  (api-extractor, publint, attw): wrap and normalize their output into the
  verdict model.

## 10. Milestones

### M0 — Spike (validate the two risky bets)

- Semantic snapshot serializer + normalizer over Playwright ariaSnapshot +
  computed styles, on 2 real component libraries.
- Measure: hash stability across rebases; false-invalidation rate on no-op
  refactors (CSS-in-JS hash churn, wrapper refactors); screenshot-skip rate vs.
  naive full-raster. **Targets: >70% skip on typical PRs; 0 baseline breakage
  across rebase; <2% false semantic misses on no-op refactors.**
- Fiber provenance walk producing owner chains on the same libraries.
- Exit criterion: normalization quality is achievable, or the ruleset needs
  redesign before anything else is built.

### M1 — Core loop (OSS launch candidate)

- `va` CLI: Stage 0 (file-level reachability) + Stage 1 (hash, diff, banding) +
  manifest read/write + `approve`.
- Storybook subject adapter (stories as subjects); plain-Playwright adapter.
- GitHub Action + docket PR comment.
- Launch narrative: "we skipped 95% of your screenshots and your baselines
  survived a rebase." Target the open Storybook-9 non-Chromatic gap.

### M2 — Attribution + agent surface

- Explanation sets, root/collateral docket, one-action root approval,
  mass-invalidation flow.
- MCP server + agent skill; demo: agent self-corrects an undeclared geometry
  change before opening the PR.
- Token dimension (resolved token table + token-keyed attribution).

### M3 — Multi-dimension + hierarchy

- API-surface dimension (wrapped collectors → verdict model, semver mapping).
- Stage 2 raster fallback with pixel→component projection; `unexplained` alarm.
- Cross-repo `inherited` (DS manifest consumption). Frequency reports.

### M4 — Governance (first revenue)

- Hosted review surface over user storage; org policy tier; audit trail.

**Pivot triggers:** if Argos ships content-addressed semantic memoization (they
have ARIA snapshots and are one step away) ⇒ concentrate on M2/M3
differentiation (attribution, agent verdicts, multi-dimension). If Playwright
ships baseline memoization ⇒ become the attribution/verdict/review layer above
it.

## 11. Open Questions

1. **Environment-key completeness** — the "same hash ⇒ same pixels" guarantee is
   only as strong as the key's coverage of render inputs (fonts, media queries,
   animation settle, external assets). The key derivation deserves
   validator-grade rigor and its own test suite. What is the audit procedure for
   key coverage gaps?
2. **Props digest stability** — non-serializable props (functions, elements) need
   a stable digest strategy that neither over- nor under-invalidates.
   Identity-based? Shape-based? Declared-opaque?
3. **Computed-style allowlist scope** — too narrow misses real regressions, too
   wide reintroduces snapshot fatigue. Versioned allowlist with per-project
   extensions? What is v1?
4. **Intent contract format** — changeset-style file vs. PR-body convention vs.
   agent-emitted manifest. Must be writable by both humans and agents.
5. **Subject discovery for pages** — stories are self-enumerating; app routes are
   not. Route-manifest adapters (Next.js first)?
6. **Concurrent renders / RSC** — server components have no client fiber;
   provenance for RSC-rendered subtrees needs a strategy (build-time
   annotation?).
7. **Naming of the "authority" framing** — validate "authority/adjudication" vs.
   "gate/verdict/contract" language with the target audience before locking
   marketing.

## 12. Success Criteria (v1, twelve weeks post-M1 launch)

- ≥3 external repos running the Action in CI on real PRs.
- Measured median CI cost: semantic stage <10% of the wall-time of the equivalent
  full-raster run on the same repos.
- Zero reported baseline invalidations caused by rebases/merges.
- At least one documented agent workflow (Claude Code or Copilot agent) consuming
  verdicts via MCP/skill and self-correcting pre-PR.
- Docket review time for a global-token PR (300+ collateral): one approval
  action, under one minute.
